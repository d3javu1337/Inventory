# Тестовые данные локального MVP

`init-test-data.sql` дополняет **текущую** БД после применения EF Core migrations.
Это не дамп схемы и не PostgreSQL entrypoint: на существующем volume entrypoint
не запускается повторно. Скрипт нужно применить явно.

Обёртка сначала применяет `repair-test-data.sql`: однократное исправление прежних
тестовых UUID и неверных режимов расписаний. Для новой БД оно ничего не меняет.
UUID нового набора — детерминированные UUIDv7. Старые тестовые UUID заменены
с сохранением внешних ссылок; ранее изготовленные метки именно `MVP-*` нужно
создать заново. Настоящие ОС и их QR не менялись. Ремонт проверен на восстановленной
копии; резервная копия до него — `backups/pre-fixture-repair-20261004`.

Из корня проекта в Bash после запуска локальных сервисов:

```bash
./deploy/deploy.sh up
./deploy/deploy.sh seed
```

`seed` берёт пользователя и имя базы из контейнера PostgreSQL. Для отдельного
локального стенда передайте перед `seed` те же `--project-name`, `--env-file` и
`--override`, что и при `up`. Кеш справочников обновляется в течение 30 секунд.

Для запуска через существующую PowerShell-обёртку:

```powershell
./deploy/init-test-data.ps1
```

Обёртка намеренно работает только с `deploy-postgres-1 / asset_inventory`.
SQL находится в транзакции; `ON_ERROR_STOP` прекращает применение при ошибке.
Повторный запуск не дублирует записи и не сбрасывает изменения пользователя.
Конфликт зарезервированного бизнес-ключа с чужим ID вызывает rollback,
а не перезаписывает чужую запись. Очистки таблиц, изменения существующих
пользователей и их паролей нет.
Если карточка организации ещё не создана, скрипт добавляет ООО «Тестовое предприятие»
с демонстрационными реквизитами. Уже заполненная карточка сохраняется целиком.

Набор: 1000 ОС `MVP-0001…MVP-1000`, 6 подразделений, 10 помещений,
5 МОЛ, 3 инвентаризатора, 8 проверок (3 черновика, 1 отменённая и 4 готовых сценария),
2 выключенных расписания, история первоначального назначения ОС.
Основания проверок, результаты обходов и подтверждения завершённых сценариев — синтетические.
`INV-MVP-002` — черновик по первому тестовому МОЛ. Чтобы начать обход по
черновику, запустите его из админки.

| Проверка | Исполнитель | Что можно проверить |
| --- | --- | --- |
| `INV-MVP-005` | `mvp.worker1` | Активный обход по второму МОЛ. Два объекта уже найдены, один из них отмечен как повреждённый. Остальные ждут сканирования. |
| `INV-MVP-006` | `mvp.worker2` | Обход по третьему МОЛ ожидает подтверждения. Есть недостача и отметка о повреждении. После подтверждения можно скачать ИНВ-1 в PDF и XLSX. |
| `INV-MVP-007` | `mvp.worker3` | Завершённая проверка по четвёртому МОЛ. Все ОС найдены, оба формата ИНВ-1 доступны сразу. |
| `INV-MVP-008` | `mvp.worker1` | Завершённая проверка по пятому МОЛ. Одно ОС не найдено, одно повреждено. Оба формата ИНВ-1 доступны сразу. |

В завершённых сценариях каждый файл ИНВ-1 формируется при первом скачивании.

Эти сценарии создаются только при наличии действующего тестового исполнителя
и хотя бы трёх активных тестовых ОС у соответствующего МОЛ. При повторном `seed`
состав, сканы и решения по уже созданным проверкам сохраняются.

Тестовые логины: `mvp.worker1`, `mvp.worker2`, `mvp.worker3`.
Пароль всех трёх: `Manual-MVP-2026!`. Это публичные **локальные тестовые**
учётные записи с ролью InventoryEmployee, не новые администраторы.
Не применять набор на production или публичном сервере.
Авторизация существующего администратора остаётся прежней.

Рабочая web-панель: http://localhost:5173; API: http://localhost:5147.
Мобильная web-эмуляция: http://127.0.0.1:5174 (стандартный Vite proxy к API 5147).
После прямого SQL каталоги могут находиться в Redis до 30 секунд:
обёртка ждёт 31 секунду, не очищая Redis и другие ключи.
