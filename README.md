# Asset Inventory — инвентаризация основных средств по QR-кодам

[Описание проекта, ролей и сценариев](PROJECT_OVERVIEW.md)

> Этот README — основной живой контекст проекта. Перед началом работы его нужно прочитать целиком. После каждого содержательного изменения необходимо обновить разделы «План реализации», «Текущее состояние» и «Журнал изменений».

## 1. Назначение проекта

Дипломный MVP автоматизирует учет и инвентаризацию основных средств одного коммерческого предприятия. Объекты маркируются QR-кодами, а назначенный инвентаризатор сверяет их фактическое наличие с реестром через мобильное Android-приложение.

Система должна позволять:

- вести реестр основных средств;
- хранить подразделения, помещения и материально ответственных лиц (МОЛ);
- импортировать ОС из CSV/XLSX;
- генерировать отдельную PNG-этикетку с QR-кодом для каждого ОС;
- создавать плановые и событийные инвентаризации;
- автоматически выбирать одного исполнителя инвентаризации;
- сканировать QR-коды на Android-устройстве или в режиме эмуляции;
- фиксировать наличие и состояние объекта;
- выявлять недостачи, неизвестные QR и известные ОС вне области проверки;
- подтверждать итоги назначенным исполнителем;
- формировать ИНВ-1 в XLSX и PDF;
- хранить историю и аудит действий.

### Исходные параметры

- **Объект:** учет основных средств предприятия.
- **Предмет:** технологии идентификации объектов в учетных системах.
- **Организация:** одно коммерческое предприятие.
- **Масштаб:** до 10 000 основных средств.
- **Язык интерфейсов:** русский.
- **Валюта:** RUB.
- **Часовой пояс отображения:** Asia/Yekaterinburg; в БД время хранится в UTC.

## 3. Технологический стек

### Backend

- .NET 10 LTS и C# 14.
- ASP.NET Core Minimal API. MVC-контроллеры не используются.
- Endpoint группируются по функциональным модулям через `MapGroup` и отдельные методы регистрации маршрутов; обработчики не должны содержать бизнес-логику и делегируют ее Application-слою.
- Entity Framework Core и Npgsql.
- PostgreSQL — единственный источник истины.
- Redis — кеш справочников, счетчиков dashboard и ограничение частоты запросов. Задания и результаты инвентаризации в Redis не хранятся.
- OpenAPI — источник контрактов и генерируемых TypeScript-клиентов.
- RFC 7807 `ProblemDetails` — единый формат ошибок.
- Фоновые задачи — hosted services внутри монолита.
- Серверная генерация QR PNG, XLSX и PDF.

Версия закреплена через `backend/global.json`: .NET SDK 10.0.401, target framework `net10.0`, язык C# 14. Контейнерная сборка также должна использовать .NET 10.

### Web

- React + TypeScript + Vite.
- React Router.
- TanStack Query.
- React Hook Form.
- MUI.
- API-клиент, сгенерированный по OpenAPI.

### Mobile

- Bare React Native.
- Целевая платформа MVP — Android.
- Работа только онлайн.
- Камера для QR, браузерная демонстрация через OBS и ручной ввод UUID в debug-сборке.
- React Navigation и TanStack Query.
- Refresh token хранится в Android Keystore.

### Deployment

Docker Compose поднимает:

- `api` — ASP.NET Core API и hosted workers;
- `web` — собранную SPA и reverse proxy;
- `postgres`;
- `redis`.

PostgreSQL и документы используют именованные volumes. Android-эмулятор подключается к API по адресу хоста.

## 4. Нормативные и предметные ограничения

Система проектируется для коммерческой организации с учетом Федерального закона № 402-ФЗ и ФСБУ 28/2023 «Инвентаризация», применяемого с 1 апреля 2025 года.

Поддерживаемые основания:

- плановая инвентаризация перед годовой отчетностью;
- смена или увольнение МОЛ;
- передача или возврат активов;
- утрата или повреждение;
- чрезвычайная ситуация;
- реорганизация;
- ликвидация;
- иное основание с обязательным описанием.

Увольнение создает проверку только тогда, когда сотрудник является МОЛ и за ним закреплены активные ОС.

ИНВ-1 используется как выбранный предприятием шаблон. Форма должна быть утверждена учетной политикой организации. Системное подтверждение пользователя не является КЭП; PDF содержит строки для ручных подписей.

## 5. Роли

### Administrator

- ведет ОС и справочники;
- импортирует данные и генерирует QR;
- управляет сотрудниками и учетными записями;
- настраивает расписания;
- регистрирует смену МОЛ;
- создает, запускает и отменяет проверки;
- заменяет назначенного исполнителя до запуска;
- видит прогресс и расхождения;
- выгружает отчеты и просматривает аудит.

Администратор не может подтвердить отчет вместо назначенного исполнителя.

### InventoryEmployee

Сотрудник отдела инвентаризации с учетной записью:

- видит назначенные проверки;
- сканирует ОС;
- фиксирует состояние;
- просматривает прогресс;
- подтверждает или отклоняет результат;
- завершает неполный обход назначенной ему инвентаризации.

### Материально ответственное лицо

МОЛ хранится как кадровая запись: UUIDv7, условный номер сотрудника и ФИО. Доступ к приложению ему не требуется.

## 6. Модель данных

Для идентификаторов бизнес-сущностей используется UUIDv7, генерируемый приложением.

### Справочники и безопасность

- `organizations`: реквизиты предприятия для отчетов;
- `departments`: подразделения и признак отдела инвентаризации;
- `locations`: помещения подразделений;
- `employees`: номер, ФИО, подразделение, занятость и признак МОЛ;
- `user_accounts`: сотрудник, логин, хеш пароля, роль и блокировка;
- `refresh_tokens`: хеш токена, устройство, срок, отзыв и цепочка ротации.

### Основные средства

`assets` содержит:

- UUIDv7, который записывается в QR;
- уникальный инвентарный номер;
- наименование;
- бухгалтерский счет;
- заводской или серийный номер;
- год выпуска;
- дату принятия к учету;
- первоначальную стоимость `numeric(19,2)`;
- подразделение, помещение и МОЛ;
- статус эксплуатации;
- признак и дату архивирования;
- данные optimistic concurrency.

`asset_assignment_history` хранит историю смены МОЛ, подразделения и помещения.

Удаление ОС запрещено: используется архивирование. Архивные ОС не входят в новые проверки, но сохраняются в старых снимках и отчетах.

### Инвентаризации

- `inventory_schedules`: период, следующая дата и режим `CreateDraft`/`AutoStart`;
- `integration_events`: внешний `eventId`, тип, исходный JSON, статус, попытки, следующая попытка и ошибка;
- `inventories`: номер, тип, основание, даты, статус, инициатор и источник;
- `inventory_asset_snapshots`: неизменяемый снимок ОС на момент запуска;
- `commission_members`: единственный назначенный исполнитель и его подтверждение (историческое имя таблицы сохранено для совместимости);
- успешный скан фиксируется в `inventory_asset_snapshots` (результат, состояние, комментарий, время и пользователь); отдельная таблица `asset_scans` не требуется;
- `unexpected_scans`: неизвестные и внеобластные QR;
- `generated_documents`: метаданные XLSX/PDF, путь и SHA-256;
- `audit_logs`: субъект, действие, объект, время, IP/device, correlation ID и безопасные изменения;
- импорт синхронный: dry-run и построчные ошибки возвращаются без записи в БД, ошибки выгружаются отдельным CSV; таблицы `import_jobs`/`import_errors` не используются.

Ограничения:

- уникальны логин, номер сотрудника, инвентарный номер, номер проверки и внешний `eventId`;
- в одной проверке допустим только один успешный скан каждого ОС;
- завершенные снимки и документы не изменяются каскадно;
- денежные значения не используют `float` или `double`.

## 7. Бизнес-процессы

### Жизненный цикл

```text
Draft → Active → AwaitingConfirmation → Completed
                     ↓
               ReviewRequired

Draft / Active / AwaitingConfirmation → Cancelled
```

1. В `Draft` администратор проверяет основание, область и исполнителя.
2. При запуске создается неизменяемый снимок ОС.
3. В `Active` назначенный исполнитель сканирует имущество.
4. Если найдены все ожидаемые ОС, сбор закрывается автоматически.
5. Если часть не найдена, назначенный исполнитель завершает обход; остаток получает `NotFound`.
6. Исполнитель повторно вводит пароль и подтверждает результат.
7. Отклонение с причиной переводит проверку в `ReviewRequired`.
8. После исправления предыдущее подтверждение сбрасывается.
   При повторном запуске после отклонения область и учетный снимок сохраняются, а результаты, состояние, комментарии и неожиданные QR сбрасываются для нового обхода. Прежние наблюдения остаются в аудите.
9. Подтверждение, фиксация реквизитов отчета и метаданные обоих файлов XLSX/PDF сохраняются в одной транзакции. Сбой формирования откатывает подтверждение.

После запуска менять исполнителя нельзя. При необходимости проверка отменяется и клонируется с новым исполнителем.

Отмененную или завершенную проверку администратор может использовать как основу нового черновика (`POST /inventories/{id}/clone`, новая плановая дата). Сохраняются тип, основание и правило области; новое назначение выполняется заново и может быть заменено до запуска. Сканы, подтверждения, отчеты и связь с периодом расписания/HR-событием не копируются. При запуске фиксируется актуальный реестр, а `SourceInventoryId` связывает новую проверку с исходной без изменения ее результатов.

### Плановая проверка

- Правило настраивает администратор.
- Начальный шаблон — ежегодно перед отчетностью.
- Область — все активные ОС предприятия.
- `CreateDraft` создает черновик.
- `AutoStart` формирует снимок, назначает исполнителя и запускает проверку.
- Дубликат одного правила и периода блокируется.

Worker блокирует каждое наступившее правило через `FOR UPDATE SKIP LOCKED`; создание проверки, автозапуск и перенос `NextRunAt` выполняются в одной транзакции. Уникальный индекс `(SourceScheduleId, ScheduledPeriod)` закрепляет запрет дублей в БД. Период — календарный месяц плановой даты в UTC; старые черновики с маркером `Расписание:...` переиспользуются без удаления. Один проход обрабатывает до 20 наступивших периодов.

Ошибка одного расписания откатывает его период и журналируется с ID правила. Другие правила продолжают выполняться, а неудавшийся период можно обработать в следующем проходе.

Повторы сохраняют местное время Екатеринбурга и выбранное число месяца. Если в целевом месяце такого числа нет, запуск приходится на последний день, а в следующем подходящем месяце возвращается к выбранному числу. В сохранённых расписаниях исходной точкой служит текущая дата следующего запуска.

### Событийная проверка

- Смену МОЛ регистрирует администратор через web.
- Увольнение приходит на внутренний endpoint.
- Endpoint сохраняет событие и отвечает `202 Accepted`; обработку выполняет worker.
- Worker читает события из PostgreSQL транзакционно через `FOR UPDATE SKIP LOCKED`.
- Область — все активные ОС, закрепленные за указанным МОЛ.
- Событие по не-МОЛ или МОЛ без ОС завершается без проверки и показывается администратору.
- Повтор с тем же `eventId`, сотрудником, датой и типом возвращает исходное событие с первоначальным описанием. Другой сотрудник, дата или тип под прежним ID возвращают конфликт.
- Ошибки повторяются с задержкой, затем переходят в `Failed`.
- Событие смены/увольнения МОЛ сразу запускает созданную проверку: в той же транзакции назначается исполнитель и фиксируется снимок ОС. Worker проверяет очередь каждые 15 секунд. Если подходящего исполнителя нет, проверка сохраняется как `NeedsAttention`, а событие содержит объяснение.
- `ResultMessage` сохраняет результат обработки на момент события: проверка запущена, требуется внимание, сотрудник не найден/не МОЛ или у него нет активных ОС. Старые результаты без этого поля не пересчитываются по изменившемуся реестру.
- Для `Failed` администратор может запросить повтор через web. Повтор использует прежние UUID, внешний `eventId` и payload; начинает новый цикл из пяти попыток и записывается в аудит. Обрабатываемые/успешные события и события с созданной проверкой повторно в очередь не ставятся.

Одновременные запросы одного `eventId` сериализуются advisory-lock PostgreSQL и возвращают одну запись. Worker обрабатывает до 20 событий за проход, каждое — в собственной транзакции. Ошибка записи откатывает бизнес-изменения до savepoint, но сохраняет номер попытки и ошибку; остальные события продолжают обрабатываться. Перед повторными попытками действуют задержки 15, 30, 60 и 120 секунд; пятая ошибка переводит событие в `Failed`. `NextAttemptAt` хранится в БД и отображается в web, поэтому перезапуск worker не сбрасывает ожидание.

Внутренний endpoint работает без прикладной авторизации только в доверенной сети, не публикуется наружу и ограничивается сетевыми правилами и размером тела.

В локальном Docker Compose порт API `5147` привязан только к `127.0.0.1`; HR-интеграция доступна с самого host или из доверенной Docker-сети. Не публикуйте этот порт на внешнем интерфейсе. В production внешний reverse proxy должен пропускать только публичные `/api/v1` маршруты, исключая `/internal`.

### Исполнитель

- Один исполнитель случайно выбирается из активных пользователей отдела инвентаризации.
- Проверяемый МОЛ исключается.
- До запуска администратор может заменить исполнителя.
- Если подходящих кандидатов нет, запуск блокируется.
- Назначение и замены записываются в аудит.

### Сканирование

QR содержит каноническую строку UUIDv7 объекта. Этот идентификатор можно распечатать на этикетке сразу после сохранения ОС, независимо от расписания и обходов. В карточке ОС кнопка «Печать» открывает этикетку для печати, а «Скачать QR» сохраняет её в PNG.

Результаты:

- `Found` — ОС входит в проверку;
- `NotFound` — ОС осталось непросканированным;
- `UnknownQr` — UUID некорректен или отсутствует в реестре;
- `OutOfScope` — объект известен, но не входит в событийную проверку.

Состояние объекта:

- `Serviceable`;
- `Damaged`;
- `Unusable`.

Для `Damaged` и `Unusable` комментарий обязателен. Геолокация, фактическое помещение и фотографии не входят в MVP.

Повторный или конкурентный скан не создаёт новую запись в том же обходе, в том числе для неизвестного QR и для ОС вне состава проверки. Пробелы по краям удаляются, а UUID сравниваются независимо от регистра. Посторонние QR видны в результатах, обход можно завершить.

### Импорт, QR и отчет

- CSV UTF-8 и XLSX импортируются по опубликованному шаблону.
- Заголовок и данные содержат ровно 10 столбцов. Лишние значения в CSV/XLSX не отбрасываются молча: заголовок отклоняется, ошибка строки показывается в dry-run и блокирует применение файла.
- Коды подразделения/помещения и табельный номер МОЛ сначала сопоставляются с точным регистром. Поиск без учёта регистра разрешён только при единственном совпадении; неоднозначность требует уточнить код и показывается в ошибке строки. Точное совпадение с архивной записью не подменяется похожей активной записью.
- В XLSX стоимость с 14 и более цифрами целой части вводится текстом. При числовом формате предпросмотр покажет ошибку строки. Для CSV и текстовых ячеек XLSX дробная часть должна быть представима целым числом копеек.
- XLSX допускает до 128 МБ после распаковки. Для CSV и XLSX действуют пределы 20 МБ на загрузку и 10 000 строк данных.
- Сначала выполняется dry-run без изменения БД, затем подтвержденное транзакционное применение.
- При применении файла коды справочников заново сопоставляются после завершения текущего изменения справочника. Сопоставление защищено до фиксации транзакции. Dry-run не ждёт эту блокировку.
- Обязательны инвентарный номер, наименование, счет, стоимость, дата учета, подразделение, помещение и МОЛ.
- Существующее ОС обновляется по инвентарному номеру; новое создается.
- Отсутствие строки в файле не архивирует ОС.
- Ошибки доступны отдельным файлом.
- PNG-этикетка содержит QR, инвентарный номер и сокращенное наименование.
- Карточка сохранённого ОС и форма редактирования показывают PNG-этикетку. QR можно сканировать с экрана.
- [Демонстрация на Android-эмуляторе без телефона](mobile/README.md#сканирование-png-в-android-эмуляторе) использует ту же PNG-этикетку в виртуальной сцене камеры.
- [Демонстрация через OBS Virtual Camera](mobile/README.md#демонстрация-через-obs-на-одном-пк) использует камеру браузерной версии мобильного интерфейса и локальный API.
- ИНВ-1 создаётся в XLSX и PDF по структуре [формы ОКУД 0317001](https://www.consultant.ru/document/cons_doc_LAW_20359/36c11815f4ef96b56bac5fa2615d37555575f698/). Для каждого сочетания подразделения, помещения и МОЛ формируется титульный лист с распиской, вкладные листы с 13 графами и итоговый лист с местом для подписей. Итоги на вкладных и итоговом листах дублируются прописью.
- Для найденного ОС фактическое количество равно 1, фактическая стоимость берётся из учётной стоимости в снимке. Для ненайденного ОС обе фактические графы равны 0. Год выпуска берётся из снимка при старте проверки. Реквизиты приказа, аренды, паспорта и прочие поля без данных остаются пустыми для заполнения.
- XLSX хранит обычные стоимости как числа. Стоимости с 14 и более цифрами целой части записываются точным текстом с двумя десятичными знаками, чтобы сохранить копейки.
- Неизвестные и внеобластные QR выводятся приложением к отчету.
- Финальный документ неизменяем; исправление оформляется новой версией проверки.
- При скачивании готового отчёта сервер проверяет доступ и хеш файла без блокировки инвентаризации и её состава.

## 8. API

Общие правила:

- базовый путь `/api/v1`;
- JSON `camelCase`, даты ISO 8601;
- Плановые даты и время кадровых событий принимаются с часовым смещением и записываются в UTC. Исходное смещение кадрового события сохраняется в payload.
- пагинация через `page` и `pageSize`, максимум 200;
- ошибки `application/problem+json` с `code`, `traceId` и ошибками полей;
- конкурентное редактирование через `ETag`/`If-Match`;
- OpenAPI используется для генерации клиентов;
- административные операции и переходы состояний аудируются.

Основные группы:

- `/auth/web/login/start|login|initial-password|change-password|refresh|logout`;
- `/auth/mobile/login/start|login|initial-password|change-password|refresh|logout`;
- `/assets`, `/assets/imports`, `/assets/{id}/qr`;
- `/departments`, `/locations`, `/employees`, `/users`;
- `/inventory-schedules`;
- `/inventory-events/mol-change`;
- `/inventory-events/{id}/retry` — повторная постановка ошибочного события в очередь, только для администратора;
- `/inventories` и команды `start`, `cancel`, `finish-scanning`, `confirm`, `reject`;
- `/inventory-schedules`, `/inventory-events/mol-change`, `/internal/v1/hr-events/dismissals`;
- `/inventories/{id}/reports/inv-1.xlsx|pdf`;
- `/dashboard`, `/audit`;
- `/mobile/inventories` и `/mobile/inventories/{id}/scan`;
- `/internal/v1/hr-events/dismissals`;
- `/dashboard`, `/audit`, `/health/live`, `/health/ready`.

Аутентификация:

- ASP.NET Core Identity;
- access JWT — 15 минут;
- refresh token — 30 дней, хранится в БД как хеш и ротируется;
- web держит access token в памяти, refresh — в защищенной HttpOnly cookie;
- mobile хранит refresh token в Android Keystore;
- выход, блокировка и повторное применение старого refresh token отзывают цепочку;
- пользователь меняет собственный пароль через web или mobile, указывая текущий пароль и новый (8–256 символов); повторный ввод проверяется интерфейсом. Пароли в аудите не сохраняются;
- смена пароля повышает `SecurityVersion` учётной записи, отзывает прежние refresh tokens и немедленно делает старые JWT недействительными на всех устройствах. Текущий клиент получает новую пару токенов; прежние JWT без версии совместимы с версией 0 до первой смены пароля;
- частота попыток входа ограничивается через Redis.
- установка первого пароля и создание первой сессии выполняются атомарно: сбой выдачи токенов оставляет возможность повторить установку; конкурирующие запросы принимают только один пароль. Если во время запроса пользователь заблокирован, пароль и сессия не сохраняются;
- описание устройства/User-Agent в сессии ограничено 300 UTF-16 единицами без разрыва суррогатной пары; длинные метаданные не мешают входу, refresh и смене пароля.

## 10. Надежность и эксплуатация

- Создание проверки, снимка и назначения исполнителя транзакционно.
- Проверка ссылок ОС и запись карточки/истории защищены общей транзакционной блокировкой с изменениями справочников. Сохранения разных ОС идут параллельно; архивирование/перенос помещения, архивирование сотрудника и снятие признака МОЛ ждут завершения записи и повторно проверяют связи. При применении импорта защита держится до commit/rollback всего файла; изменения справочников в это время ожидают. После ожидания используются актуальные значения из БД, а не ранее отслеживаемая EF-копия.
- Переходы статусов проверяются доменом и БД.
- Worker использует блокировку строк, счетчик попыток и экспоненциальную задержку.
- Генерация отчетов идемпотентна.
- Redis работает по cache-aside: справочники/организация/список пользователей — TTL 30 секунд, dashboard — 5 секунд. После commit меняется общая generation группы; rollback и поздний читатель не публикуют незакоммиченные данные в актуальный кеш. Базы, использующие общий Redis, изолированы namespace.
- При отказе Redis чтение идёт в PostgreSQL с ограниченным ожиданием кеша. API запоминает изменения, которые не удалось опубликовать, и при первом чтении после восстановления Redis обновляет поколение группы перед обращением к кешу. Другой API-экземпляр может показывать прежние справочники до смены поколения или истечения TTL. Авторизация, бизнес-валидация и команды всегда проверяют БД.
- В Docker Nginx обновляет адрес API по DNS после пересоздания контейнера. Для загрузки файла импорта учитывается размер multipart-запроса, при этом API проверяет лимит файла в 20 МБ.
- Логи структурированы и содержат `traceId`, пользователя, inventory ID и event ID.
- Пароли, токены и полные строки импорта не логируются.
- Секреты передаются через environment/secrets.
- Целевая среда по решению владельца — локальный MVP: API/web/Metro привязаны к loopback, PostgreSQL/Redis не публикуются на host. Development-ключи и HTTP допустимы только в этой доверенной локальной среде.
- Вне Development запуск отвергает дефолтный JWT-ключ, локальный пароль БД и не-HTTPS/wildcard CORS. Forwarded headers доверяются только loopback/явным IP proxy; production refresh-cookie всегда Secure. Настоящие HTTPS-домен, Android URL и отдельная подпись остаются условиями будущего распространения, не текущего MVP.
- Readiness проверяет PostgreSQL, Redis и файловое хранилище.
- Нужны резервное копирование и восстановление БД и документов.
- Границы локального доступа и остаточные dependency-риски описаны в [SECURITY.md](SECURITY.md). Audit не заменяет ревью; локальный MVP нельзя публиковать в сеть с Development-секретами.

## 15. Текущее состояние

Баш-скрипт [deploy/deploy.sh](deploy/deploy.sh) собирает и запускает стек, проверяет доступность API и веб-панели, показывает статус и логи и останавливает контейнеры с сохранением данных. Команды для основного и демонстрационного стендов описаны в [инструкции по запуску](deploy/README.md#деплой-из-bash).

Новые выгрузки используют бланк ИНВ-1 с 13 графами, распиской МОЛ и итогами по страницам. Снимок фиксирует год выпуска и идентификаторы подразделения, помещения и МОЛ. Старые сохранённые выгрузки продолжают выдаваться из хранилища по исходной контрольной сумме.

Общие правила Git исключают локальные конфигурации, резервные копии, временные файлы и рабочую папку курсовой. Модульные правила исключают зависимости и результаты сборок и тестов. В состав первого коммита входят шаблоны `.env.example`, lock-файлы, Gradle Wrapper и тестовый Android debug-keystore, который используется локальной сборкой.

Сканирование и debug-ввод используют UUID ОС. В разделе мобильного приложения приведены команды для запуска виртуальной сцены камеры и загрузки PNG в эмулятор.

OpenAPI помечает защищённые маршруты схемой JWT Bearer и показывает заголовки условного обновления карточки. Веб-формы создания инвентаризации, назначения, расписания и события проверяют типы запросов по сгенерированной схеме.

Рабочая PostgreSQL хранит назначения исполнителей в `inventory_assignments`. Три внешних ключа защищают историю закреплений, отчёты и посторонние сканы. Действующие клиенты используют `/assignee` и поле `assignee`. Прежний маршрут `/commission` и поле `commission` поддерживают ранее выпущенные клиенты. Редактирование карточки ОС возвращает HTTP 412 для устаревшего `If-Match` и HTTP 428 при отсутствии заголовка.

В локальной админке QR-этикетка видна в карточке и при редактировании ОС. Chrome на изолированной базе подтвердил, что предпросмотр совпадает со скачанным PNG и помещается на экране шириной 390 пикселей. Рабочая админка обновлена, сверка таблиц и файлов отчётов прошла.

Вход в другой аккаунт закрывает устаревшие вкладки админки и мобильного веба. Реактивное обновление токена сверяет владельца сессии до повторной отправки команды. В Chrome после естественного истечения токена старая вкладка выполнила один PUT, получила 401 при обновлении с чужой cookie и оставила карточку и сессию второго администратора в рабочем состоянии.

Админка принимает и показывает точную стоимость ОС до 99 999 999 999 999 999,99 ₽. Обязательное поле стоимости сохраняется без округления при изменении других данных. Снимок ранее начатой проверки сохраняет исходную стоимость. Работника любого активного подразделения можно связать с администратором. Для роли инвентаризатора требуется работник отдела инвентаризации.

Восстановление копии сверяет перечень файлов, выполняет пробное восстановление и использует проверенную копию для переноса. Перед запуском API сверяются записанные файлы и отзываются прежние токены. Изолированная проверка подтвердила отказ по прежним access- и refresh-токенам, новый вход и скачивание обоих отчётов.

Каждый запуск инвентаризации увеличивает номер обхода в той же транзакции, что создаёт или очищает снимок. Мобильные команды передают `expectedRound` из открытого экрана. Сервер сверяет его после блокировки строки, поэтому задержанная команда из старого обхода получает HTTP 409 до изменения текущих результатов. Миграция `InventoryRound` назначает существующим записям номер 0. Для прежних клиентов параметр остаётся необязательным.

Полный Bash-прогон прошли 289 тестов. В мобильном Chrome открытая до повторного запуска форма отправила номер 0 и получила HTTP 409. Свежая форма подтвердила обход 1 один раз. Старый запрос без `expectedRound` вернул HTTP 200 с полной карточкой. После применения миграции к локальному стенду контрольные суммы существовавших полей и отчётов совпали.

После фактического истечения access-токена мобильный Chrome получил 401, выполнил один refresh и повторил подтверждение с тем же телом и номером обхода. Сервер вернул 409, а новый обход затем подтвердился один раз. На Android API 34 кадровая проверка появилась в открытом списке через 11,51 секунды. Эмулятор отправил номер 1 при завершении и подтверждении, а сохранённые PDF и XLSX совпали с серверными по SHA-256.

За 38 минут изолированного прогона выполнено 4 514 HTTP-запросов, 19 кадровых циклов и семь повторных обходов. Все 28 запоздалых команд получили HTTP 409, токены обновились четыре раза после 401. PostgreSQL подтвердил 38 отчётов и по одной записи подтверждения на цикл. Тестовая копия с 44 документами восстановилась в отдельном PostgreSQL, контрольные суммы рабочих данных и отчётов совпали после прогона.

Для ранее обработанного кадрового события со старым черновиком технический сбой автозапуска оставляет черновик без частичного снимка, сохраняет дату повтора через 30 секунд и позволяет запустить следующие черновики. После восстановления существующая инвентаризация запускается с тем же ID. На демобазе оба черновика получили ровно один снимок и одну запись запуска.

Повтор отклонения с той же причиной проверяет назначение и пароль, после чего возвращает сохранённое решение. В мобильном Chrome потеря ответа после записи отклонения и повторная отправка оставили одну запись аудита. В web зависший запрос авторизации прерывается через 15 секунд. Ошибка сети сохраняет возможность повторить действие, а обновление рабочей сессии по-прежнему начинается после 401.

На собранной админке намеренно зависший refresh освободил форму за 15,1 секунды, следующий вход вернул HTTP 200. После реального истечения другого access-токена Chrome выполнил PUT 401, один refresh 200 и повтор исходного PUT 200 с прежним `If-Match` и содержимым формы.

В дополнительном Bash-прогоне прошли 288 тестов (162 backend, 21 web unit, 41 web Playwright, 62 mobile Jest и 2 mobile Playwright), сборки, проверки типов и линт. Локальные API и web обновлены на этих образах. Контрольные суммы рабочих таблиц и отчётов до и после запуска совпали.

На Android API 34 кадровая проверка появилась в открытом списке через 28,73 секунды от отправки события в этом прогоне. На эмуляторе завершён обход, введён пароль подтверждения и сохранены PDF и XLSX через системный диалог. Контрольные суммы сохранённых файлов совпали с серверными.

Заключительный дополнительный прогон длился 33 минуты. Выполнено 3 828 запросов, 17 событийных циклов, шесть повторных отклонений, четыре реактивных refresh и 68 скачиваний. PostgreSQL подтвердил 34 отчёта по 17 циклам без частичных записей. Демокопия с 38 документами прошла пробное восстановление. За 208 раундов проверки рабочего стенда один запрос попал на плановый перезапуск API при обновлении.

Очереди расписаний и кадровых событий выполняются независимо. Неудачный период расписания откатывается и повторяется с растущей задержкой от 15 секунд до 5 минут. В админке видны число попыток и время следующего повтора. Сохранение расписания сбрасывает задержку. Проверены 20 одновременных ошибок, выполнение соседнего расписания и сохранность состояния после перезапуска.

Мобильное завершение обхода одним SQL-обновлением переводит только ожидающие позиции в «Не найдено». Повтор завершения и подтверждения возвращает уже сохранённый результат, при подтверждении повторно проверяется пароль. Мобильные команды `finish-scanning`, `confirm` и `reject` используют `includeDetails=false` и получают HTTP 204. По умолчанию сохранён полный ответ HTTP 200. На 10 006 ОС медиана завершения составила 126 мс против 1,38 с. Ответ команды сократился с 7,9 МБ до нуля, следующая страница занимает около 16 КБ. На подтверждение с генерацией двух отчётов мобильный клиент выделяет до 60 секунд.

При выходе из админки форма входа открывается сразу, а изменения общей cookie сериализуются. Справочники и формы расписаний открываются без ошибки предыдущей команды. Новая форма пользователя очищает логин и пароль, а форма кадрового события открывается с новым пустым Event ID. В Chrome на демобазе проверены создание, правка и архивирование подразделений, помещений и сотрудников, блокировка и разблокировка пользователя, редактирование расписания и обработка кадрового события.

В форме импорта неудачная перепроверка снимает разрешение на применение, а следующий успешный запрос очищает сообщение об ошибке. Через Chrome проверены XLSX с кириллицей и дробной стоимостью, отказ на неизвестном коде подразделения, сухой прогон без записи и успешное применение после 503.

Сервисы Compose перезапускаются после сбоя процесса. Скрипт восстановления очищает Redis только выбранного проекта перед открытием API. На отдельной базе после восстановления первый ответ больше не содержал запись из прогретого кеша предыдущей версии БД.
